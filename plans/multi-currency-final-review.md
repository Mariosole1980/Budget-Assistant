# Multi-Currency — Τελικό Τεχνικό Review (Πριν την Υλοποίηση)

**Σκοπός:** Τελικό τεχνικό review σε 5 σημεία που πρέπει να ξεκαθαριστούν πριν την
υλοποίηση, ώστε η εφαρμογή να είναι απλή για καθημερινή χρήση αλλά η αρχιτεκτονική να
αντέχει παγκόσμιους χρήστες και οικογένειες.

**Κατάσταση:** DESIGN REVIEW #5 — Τελικό τεχνικό review.

---

## 1. Ξεκαθάρισε το μοντέλο του `amount_base`

### 1.1 Το πρόβλημα

Με οικογένεια όπου τα μέλη έχουν διαφορετικό `base_currency`, πρέπει να ορίσουμε
**ακριβώς** τι σημαίνει το `amount_base` κάθε συναλλαγής, ώστε να αποφύγουμε λάθος
`SUM` σε διαφορετικά νομίσματα.

### 1.2 Απόφαση: Το `amount_base` είναι ΠΑΝΤΑ στο `base_currency` του χρήστη που δημιούργησε τη συναλλαγή

**Το `amount_base` είναι πάντα στο νόμισμα του χρήστη (creator).** Δεν είναι ποτέ στο
family reporting currency.

```
amount_base = amount / rate_to_base
όπου rate_to_base = ισοτιμία (currency → creator.base_currency) της ημερομηνίας
```

**Παράδειγμα:**
- Μέλος Α (base EUR) δημιουργεί 50 USD → `amount_base = 42.73 EUR`.
- Μέλος Β (base USD) δημιουργεί 50 USD → `amount_base = 50 USD`.

Το `amount_base` **δεν** είναι συγκρίσιμο μεταξύ μελών με διαφορετικό base_currency.

### 1.3 Ποιο είναι το source of truth;

**Source of truth:** `amount`, `currency`, `rate_to_base`, `base_currency` (του
creator). Το `amount_base` είναι **cache** — ανακατασκευάσιμο πάντα ως
`amount / rate_to_base`.

### 1.4 Ο κανόνας που αποτρέπει το λάθος SUM

**Απαγόρευση:** Ποτέ `SUM(amount_base)` σε συναλλαγές με διαφορετικό `base_currency`.

**Σωστός τρόπος για οικογενειακό report (σε reporting currency R):**

```
Family total (R) = Σ [ convert(tx.amount_base, tx.base_currency, R, tx.date) ]
```

Δηλαδή: μετατρέπουμε **κάθε** συναλλαγή ξεχωριστά από το δικό της `base_currency` στο
target currency, και **μετά** αθροίζουμε.

**Πότε επιτρέπεται το άμεσο `SUM(amount_base)`;**
Μόνο όταν **όλες** οι συναλλαγές έχουν το **ίδιο** `base_currency` (π.χ. προσωπικά
reports ενός χρήστη, ή οικογενειακό report όπου όλα τα μέλη έχουν το ίδιο base).

### 1.5 Πώς το επιβάλλουμε στον κώδικα

Προσθέτουμε στο `CurrencyService` μια μέθοδο που **ποτέ δεν αθροίζει απευθείας** σε
μικτά base_currency:

```js
// Αθροίζει συναλλαγές σε ένα target currency, μετατρέποντας κάθε μία ξεχωριστά.
sumInCurrency(transactions, targetCurrency) {
  return transactions.reduce((sum, tx) => {
    return sum + this.convert(this.toBase(tx), tx.base_currency, targetCurrency, tx.date);
  }, 0);
}
```

**Κανόνας:** Όλα τα reports χρησιμοποιούν `sumInCurrency()`. Κανένα report δεν κάνει
απευθείας `SUM(amount_base)` εκτός αν είναι εγγυημένα ομοιογενές σε base_currency.

### 1.6 Σύνοψη

| Ερώτηση | Απάντηση |
|---|---|
| Το `amount_base` είναι στο νόμισμα του χρήστη; | **Ναι**, πάντα στο `base_currency` του creator |
| Ή στο family reporting currency; | **Όχι**, ποτέ |
| Ποιο είναι το source of truth; | `amount`, `currency`, `rate_to_base`, `base_currency` |
| Πώς αποφεύγουμε λάθος SUM; | `sumInCurrency()` — μετατροπή ανά συναλλαγή |

## 2. Ανάλυση αλλαγής χώρας χρήστη

### 2.1 Το πρόβλημα

Παράδειγμα: 2026 Ελλάδα EUR, 2030 Καναδάς CAD. Πρέπει να υπάρχει ιστορικό αλλαγών
currency preference ή αρκεί ένα profile field;

### 2.2 Διάκριση: `base_currency` (σταθερό) vs `display_currency` (μεταβλητό)

- **`display_currency`:** Αλλάζει συχνά (ταξίδια, προτίμηση). **Ένα profile field
  αρκεί** — είναι καθαρά εμφάνισης και δεν επηρεάζει τα αποθηκευμένα δεδομένα.
- **`base_currency`:** Το αγκυροβόλιο αποθήκευσης. **Σύσταση: σταθερό.** Αν αλλάξει,
  απαιτεί μαζικό επανυπολογισμό.

### 2.3 Απόφαση: Δύο ξεχωριστά πεδία + προαιρετικό ιστορικό για `base_currency`

**Για το `display_currency`:** Ένα profile field αρκεί. Δεν χρειάζεται ιστορικό γιατί
δεν επηρεάζει τα δεδομένα — είναι απλώς το τρέχον νόμισμα εμφάνισης.

**Για το `base_currency`:** Χρειάζεται **προαιρετικό ιστορικό** (`base_currency_history`)
για να μπορούμε να αναπαράγουμε σωστά παλιά reports αν ο χρήστης άλλαξε base.

### 2.4 Γιατί χρειάζεται ιστορικό για το `base_currency`

Αν ο χρήστης άλλαξε `base_currency` από EUR σε CAD το 2030:
- Οι παλιές συναλλαγές (2026) έχουν `base_currency=EUR`.
- Οι νέες (2030+) έχουν `base_currency=CAD`.
- Χωρίς ιστορικό, δεν ξέρουμε **πότε** άλλαξε και **ποια** συναλλαγή ανήκει σε ποιο
  base. Με το ιστορικό, μπορούμε να αναπαράγουμε σωστά τα reports κάθε περιόδου.

```sql
CREATE TABLE public.base_currency_history (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id       UUID REFERENCES auth.users(id) ON DELETE CASCADE,
    base_currency TEXT NOT NULL REFERENCES public.currencies(code),
    changed_at    TIMESTAMPTZ DEFAULT now(),
    note          TEXT
);
```

**Σημείωση:** Αυτό είναι **προαιρετικό** και χρειάζεται μόνο αν επιτρέψουμε αλλαγή
`base_currency`. Αν το `base_currency` είναι πραγματικά σταθερό (σύσταση), το ιστορικό
είναι απλώς audit και όχι κρίσιμο για τον υπολογισμό.

### 2.5 Σύνοψη

| Αλλαγή | Πεδίο | Χρειάζεται ιστορικό; |
|---|---|---|
| `display_currency` (ταξίδι, προτίμηση) | `profiles.display_currency` | **Όχι** — ένα field αρκεί |
| `base_currency` (μετακόμιση χώρας) | `profiles.base_currency` | **Προαιρετικά** — `base_currency_history` για audit/αναπαραγωγή |

## 3. Ξεχώρισε: απλή μεταφορά vs ανταλλαγή νομίσματος (FX conversion)

### 3.1 Το πρόβλημα

Πρέπει να διακρίνουμε δύο διαφορετικές πράξεις που σήμερα μπορεί να μπερδευτούν στα
reports:

1. **Απλή μεταφορά χρημάτων** (transfer) — ίδιο νόμισμα, από account σε account.
2. **Ανταλλαγή νομίσματος** (FX conversion) — διαφορετικό νόμισμα, με ισοτιμία.

### 3.2 Απόφαση: Δύο ξεχωριστοί τύποι

Προσθέτουμε ξεχωριστούς τύπους συναλλαγής:

```sql
type TEXT CHECK (type IN (
    'expense', 'income',
    'transfer',        -- απλή μεταφορά, ίδιο νόμισμα
    'fx_conversion'    -- ανταλλαγή νομίσματος, διαφορετικό νόμισμα
))
```

### 3.3 Πώς διαφέρουν

| Χαρακτηριστικό | `transfer` | `fx_conversion` |
|---|---|---|
| Νόμισμα | Ίδιο (EUR→EUR) | Διαφορετικό (EUR→USD) |
| Ισοτιμία | Δεν χρειάζεται (1:1) | Χρειάζεται (`transfer_rate`) |
| Σκέλη | 2 (out + in) | 2 (out + in) |
| Επίδραση στο net worth | Καμία | Καμία (μόνο FX gain/loss) |
| Εμφάνιση στα reports | Εξαιρείται | Εξαιρείται από έξοδα/έσοδα, FX gain/loss ξεχωριστά |

### 3.4 Πώς αποφεύγεται η σύγχυση στα reports

- **Reports εξόδων/εσόδων:** Εξαιρούνται και τα `transfer` και τα `fx_conversion`.
- **Budgets:** Εξαιρούνται και τα δύο.
- **FX gain/loss:** Μόνο τα `fx_conversion` δημιουργούν FX gain/loss, το οποίο
  εμφανίζεται σε ξεχωριστή γραμμή (όχι ως έξοδο/έσοδο).

### 3.5 Σύνοψη

| Πράξη | Τύπος | Ισοτιμία | Στα reports |
|---|---|---|---|
| Μεταφορά EUR→EUR | `transfer` | Όχι | Εξαιρείται |
| Ανταλλαγή EUR→USD | `fx_conversion` | Ναι (`transfer_rate`) | Εξαιρείται από έξοδα, FX ξεχωριστά |

## 4. UX Κανόνες για την επιλογή νομίσματος

### 4.1 Αρχή

**Ο χρήστης δεν πρέπει να γνωρίζει τεχνικούς όρους** (base_currency, rate_to_base,
amount_base, ισοτιμία αναφοράς κ.λπ.). Η επιλογή νομίσματος πρέπει να είναι
**αυτόματη και φυσική**.

### 4.2 Ροή επιλογής νομίσματος

Όταν ο χρήστης εισάγει συναλλαγή, το νόμισμα επιλέγεται με ιεραρχία:

1. **Αυτόματη πρόταση από το account:** Αν ο χρήστης επιλέξει account, το νόμισμα
   συμπληρώνεται αυτόματα από το `account.currency`. **Ο χρήστης δεν το σκέφτεται.**
2. **Αυτόματη πρόταση από χώρα:** Αν η εφαρμογή γνωρίζει τη χώρα (GPS/γλώσσα/χειροκίνητη
   ρύθμιση), προτείνει το τοπικό νόμισμα (π.χ. Ιαπωνία → JPY).
3. **Πρόσφατα χρησιμοποιούμενα:** Εμφανίζονται τα νομίσματα που χρησιμοποίησε πρόσφατα
   ο χρήστης (π.χ. EUR, USD, JPY).
4. **Προτεινόμενα:** Τα πιο συνηθισμένα (EUR, USD, GBP, JPY, CAD, AUD, CHF).
5. **Αναζήτηση:** Ο χρήστης μπορεί να ψάξει με όνομα χώρας ή κωδικό ("Ιαπωνία",
   "JPY", "¥").

### 4.3 Οπτική παρουσίαση

```
[ Νόμισμα:  USD  ▼ ]
  ┌─────────────────────────┐
  │ 🇺🇸 US Dollar (USD)      │  ← προτεινόμενο (από χώρα/account)
  │ 🇪🇺 Euro (EUR)           │  ← πρόσφατο
  │ 🇯🇵 Japanese Yen (JPY)   │  ← πρόσφατο
  │ ─────────────────────── │
  │ 🔍 Αναζήτηση...         │
  └─────────────────────────┘
```

### 4.4 Κανόνες UX

1. **Ποτέ τεχνικοί όροι** — μόνο "Νόμισμα", "Ποσό", "Ισοτιμία" (αν χρειαστεί).
2. **Αυτόματη μετατροπή:** Ο χρήστης βλέπει "5 USD = 4.27 EUR" χωρίς να κάνει τίποτα.
3. **Χειροκίνητη ισοτιμία κρυμμένη:** Πίσω από "Προχωρημένες επιλογές" — μόνο αν ο
   χρήστης τη χρειαστεί (π.χ. από την τράπεζά του).
4. **Σαφής ένδειξη εκτίμησης:** Αν η ισοτιμία είναι cached (offline), "⚠️ Εκτίμηση".
5. **Αυτόματη πρόταση χώρας:** Αν ο χρήστης είναι σε ξένη χώρα, προτείνεται το τοπικό
   νόμισμα — ιδανικό για ταξίδια.

### 4.5 Σύνοψη

| Μέθοδος | Πότε |
|---|---|
| Από account | Πάντα (προεπιλογή) |
| Από χώρα | Αν γνωστή |
| Πρόσφατα | 2η επιλογή |
| Προτεινόμενα | 3η επιλογή |
| Αναζήτηση | Τελευταία λύση |

## 5. Επιβεβαίωση: Το CurrencyService είναι ο μοναδικός μηχανισμός conversions

### 5.1 Απόφαση

**Ναι.** Το `CurrencyService` είναι ο **μοναδικός** μηχανισμός που κάνει μετατροπές
νομίσματος. Κανένα άλλο σημείο του κώδικα δεν υπολογίζει ισοτιμία ή `amount_base`.

### 5.2 Πώς το διασφαλίζουμε

1. **Κεντρικοποίηση:** Όλες οι μετατροπές περνούν από το `CurrencyService`:
   - `convert(amount, from, to, date)` — γενική μετατροπή.
   - `computeAmountBase(...)` — μόνο αυτό θέτει `amount_base`.
   - `toBase(tx)` — επιστρέφει το ποσό στο base_currency.
   - `displayAmount(tx, target)` — για εμφάνιση.
   - `sumInCurrency(txs, target)` — αθροίσεις reports.
   - `getRate(...)` / `setManualRate(...)` — ισοτιμίες.
2. **Αντικατάσταση όλων των `parseFloat(t.amount)`:** Κάθε σημείο που σήμερα κάνει
   `parseFloat(t.amount)` για στατιστικά αντικαθίσταται με `CurrencyService.toBase(t)`.
3. **Απαγόρευση απευθείας υπολογισμού:** Ο κανόνας στον κώδικα: "αν χρειάζεσαι
   μετατροπή, χρησιμοποίησε το CurrencyService. Ποτέ μην πολλαπλασιάσεις/διαιρέσεις
   ποσά με ισοτιμία εκτός του CurrencyService."
4. **Code review / lint:** Ένα lint rule ή code review checklist επιβεβαιώνει ότι δεν
   υπάρχουν απευθείας μετατροπές εκτός του service.

### 5.3 Γιατί είναι κρίσιμο

- **Συνέπεια:** Όλες οι μετατροπές χρησιμοποιούν την ίδια ιεραρχία ισοτιμίας και την
  ίδια στρογγυλοποίηση.
- **Αναπαραγωγιμότητα:** Το `amount_base` είναι πάντα `amount / rate_to_base` με τον
  ίδιο τρόπο.
- **Αποφυγή bugs:** Δεν μπορεί να υπάρξει απόκλιση μεταξύ αρχικού ποσού, ισοτιμίας και
  converted ποσού.

### 5.4 Σύνοψη

| Ερώτηση | Απάντηση |
|---|---|
| Είναι το CurrencyService ο μοναδικός μηχανισμός; | **Ναι** |
| Πώς το διασφαλίζουμε; | Κεντρικοποίηση + αντικατάσταση `parseFloat` + κανόνας κώδικα |
| Τι κερδίζουμε; | Συνέπεια, αναπαραγωγιμότητα, αποφυγή bugs |

## Συμπέρασμα

Το τελικό τεχνικό review ξεκαθαρίζει τα 5 σημεία:

1. **`amount_base`** είναι πάντα στο `base_currency` του creator (όχι στο family
   reporting currency). Source of truth = `amount`, `currency`, `rate_to_base`,
   `base_currency`. Το λάθος SUM αποφεύγεται με `sumInCurrency()` που μετατρέπει κάθε
   συναλλαγή ξεχωριστά.
2. **Αλλαγή χώρας:** `display_currency` = ένα profile field (αρκεί). `base_currency` =
   σταθερό, με προαιρετικό `base_currency_history` για audit αν επιτραπεί αλλαγή.
3. **Transfer vs FX conversion:** Ξεχωριστοί τύποι (`transfer` vs `fx_conversion`),
   και οι δύο εξαιρούνται από reports εξόδων/εσόδων, με το FX gain/loss ξεχωριστά.
4. **UX:** Ο χρήστης δεν βλέπει τεχνικούς όρους. Το νόμισμα επιλέγεται αυτόματα από
   account/χώρα, με πρόσφατα/προτεινόμενα/αναζήτηση ως εναλλακτικές.
5. **CurrencyService** είναι ο μοναδικός μηχανισμός conversions, με κεντρικοποίηση και
   αντικατάσταση όλων των `parseFloat(t.amount)`.

Η αρχιτεκτονική είναι **απλή για καθημερινή χρήση** (ο χρήστης βλέπει μόνο
"ποσό + νόμισμα") και **ανθεκτική για παγκόσμιους χρήστες και οικογένειες** (σωστή
μετατροπή, ιστορικό, transfers, FX).
