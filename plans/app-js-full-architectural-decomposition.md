## 1. The Fundamental OTA Constraint (governs every conclusion)

### 1.1 What OTA actually delivers
- The Capgo OTA bundle is generated by `npx @capgo/cli bundle zip` ([`scripts/release-native.js:86`](scripts/release-native.js:86)).
- Developer comments in [`app.js:4`](app.js:4), [`app.js:18607`](app.js:18607), [`app.js:18672`](app.js:18672) state authoritatively: **the OTA engine downloads only `app.js` + `style.css`** to existing native installs.
- `index.html` and all `js/*.js` files are **NOT** updated by OTA on native installs.

### 1.2 The three delivery paths
| Path | `index.html` + `js/*.js` updated? | New module delivered? |
|---|---|---|
| **Web/PWA** | ✅ Yes (deployed together; SW network-first fetches new modules) | ✅ Yes |
| **Native — new APK** | ✅ Yes (APK bundles full `www/`) | ✅ Yes |
| **Native — old APK + OTA** | ❌ No (old bundled `index.html` + old `js/`) | ❌ **No** |

### 1.3 Why this is the fundamental blocker
For a **new** `js/*.js` module to be safe on the **native OTA path**, one of these must hold:
1. The module is **already bundled** in old APKs — impossible for a new module.
2. `app.js` carries a **self-sufficiency guard** (the [`CurrencyService` bootstrap pattern](app.js:15)) that falls back to inline code when the module is absent — but this **re-adds the exact bytes removed**, so `app.js` does not shrink.

**Therefore: NO new `js/*.js` module can reduce `app.js` size while remaining OTA-safe for native users.** This is the single architectural fact that invalidates most "extract to a module" proposals.

### 1.4 What IS OTA-safe (without changing the pipeline)
- **Pure in-file deletion** of dead/duplicate code (no new module, no new `<script>` tag).
- **Web-only** extraction (acceptable if the feature is web-only, but this app is primarily native).
- **In-file reorganization** (moving code between sections of `app.js` itself) — no OTA impact, but no size reduction either.

> **Conclusion:** Under the *current* OTA model, **no subsystem can be extracted to a new module with a net size reduction**. The only OTA-safe "modularization" is dead-code removal and internal reorganization. Any real module extraction requires an OTA-pipeline change (out of scope, reported as a blocker).

## 6. Why the OTA Architecture Is the Fundamental Blocker (documented)

The user asked: "If the current OTA architecture is the fundamental blocker, document exactly why."

**It is the fundamental blocker, and here is the exact mechanism:**

1. **Delivery asymmetry:** OTA updates `app.js` + `style.css` only. It does **not** update `index.html` or any `js/*.js` module on native installs ([`app.js:4`](app.js:4), [`app.js:18607`](app.js:18607), [`app.js:18672`](app.js:18672), [`scripts/release-native.js:86`](scripts/release-native.js:86)).

2. **Module loading is via `index.html` `<script>` tags.** Every `js/*.js` module (including the already-extracted `constants.js`, `utils.js`, `translations.js`, `receiptStorage.js`, `transactionMerge.js`) is loaded by a `<script>` tag in `index.html`. A **new** module requires a **new** `<script>` tag in `index.html`.

3. **Old APKs keep old `index.html`.** A native user on an old APK who receives an OTA update gets the new `app.js` but the **old** `index.html` — which has **no** `<script>` tag for the new module. The new module is never loaded.

4. **Result:** If the new `app.js` calls a global from the missing module, it throws `ReferenceError` → **app crash on the native OTA path**. This is not a hypothetical — it is exactly why the existing modules are a latent risk (they have no guards except `TRANSLATIONS`).

5. **The only mitigation that preserves size reduction is impossible without an OTA change:** You cannot add a `<script>` tag to an `index.html` that OTA won't update. The self-sufficiency guard (CurrencyService pattern) works but **re-adds the removed code inside `app.js`**, so `app.js` does not shrink.

6. **Therefore:** Under the current OTA model, **the maximum achievable `app.js` reduction is the dead-code amount (~50–100 lines)**. Any meaningful (500+ line) reduction requires either (a) an OTA-pipeline change to ship new modules, or (b) accepting a crash risk on native OTA users. Both are out of scope / unacceptable.

## 7. Conclusion & Recommendation

**Verdict: DO NOT IMPLEMENT any module extraction under the current OTA architecture.**

### What this means
- **No subsystem can be extracted to a new module with a net size reduction** while remaining OTA-safe for native users.
- The **only** OTA-safe modularization actions are:
  1. **Dead-code/duplicate consolidation** (already done in Phase 1; ~50–100 more lines available via `getAccountDisplayName` consolidation — low value).
  2. **Internal reorganization** of `app.js` into clearer sections (no size benefit, but improves maintainability with zero OTA risk).
  3. **Web-only** extraction (not applicable — app is primarily native).

### The architectural win that IS achievable
The **Notes subsystem (S14, ~1,970 lines)** is the single best candidate — least coupled, self-contained, cleanest boundary. But it can only be extracted **with an OTA-pipeline change** (ship `js/notes.js` in the OTA bundle + add the `<script>` tag to `index.html`). That change is out of scope and is the **blocker**.

### Recommended path forward (for user decision)
1. **Accept the OTA constraint as-is** and stop pursuing module extraction. Keep `app.js` as a monolith, but improve internal organization (section headers, dead-code cleanup).
2. **OR** approve a **one-time OTA-pipeline change** (add new modules to the OTA bundle + update `index.html` + add self-sufficiency guards) — this is the *only* way to unlock the Notes extraction and any other 500+ line reduction. This is a deliberate architectural decision, not something to do implicitly.
