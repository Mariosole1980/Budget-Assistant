# Manual E2E Verification Procedure — Cross-Device Sync, Trash & Permanent Delete

**Scope:** Verify the full transaction lifecycle across **Android app → Supabase → Web browser** and back, including trash (soft-delete), permanent delete (hard-delete), and the stale-cache / resurrection guard.

**Precondition:** You are signed in on BOTH the Android app and the Web browser with the **same authenticated account**. Do NOT use guest mode. Do NOT touch any real transaction — only the single test transaction described below.

---

## 0. The Uniquely Identifiable Test Transaction

Use **one** transaction with a note that cannot collide with any real data:

| Field | Value |
|---|---|
| **Note** | `E2E-TEST-<your-initials>-<today>` e.g. `E2E-TEST-MK-2026-08-30` |
| **Type** | Expense |
| **Amount** | `0.01` (a value no real transaction uses) |
| **Category** | Any (e.g. "Other") |
| **Account** | Any account you own |
| **Date** | Today |

> **Why:** The note is the human-readable unique key. The **transaction `id`** is a UUID generated by the app (`generateUUID()` / `gen_random_uuid()`). You will need that UUID for the database checks in the FAIL paths — see [Appendix A](#appendix-a-where-to-find-the-transaction-id-and-state).

**Record the note string now** and reuse the **exact same** note string for every step. Do not create a second transaction.

---

## 1. Android → Supabase → Web

### Step 1.1 — Create the test transaction on Android
- **Action:** On the **Android app**, add a new expense transaction with the test note, amount `0.01`, today's date. Save it.
- **Expect:** The transaction appears immediately in the Android transaction list. The sync icon shows a brief "syncing" state, then settles. No error toast.
- **FAIL if:** The transaction does not appear locally, or an error toast appears, or the sync icon stays in an error state.

### Step 1.2 — Confirm it reached Supabase
- **Action:** Open the **Web browser** (same account). Wait ~5–10 seconds for realtime, then open the Transactions tab.
- **Expect:** The test transaction (note `E2E-TEST-…`, amount `0.01`) appears in the Web transaction list **without** you creating it manually.
- **FAIL if:** The transaction does not appear on Web after a manual sync (see Step 1.3) and a reasonable wait.
- **Where to check on FAIL:** See [Appendix A](#appendix-a-where-to-find-the-transaction-id-and-state) — query `public.transactions` for the note; confirm `status = 'active'` and `user_id` = your account.

### Step 1.3 — Force a manual sync (if realtime did not deliver)
- **Action:** On Web, tap the **cloud sync icon** in the header (or the "Sync Now" row in Settings) to call `forceSyncNow()`.
- **Expect:** The test transaction appears after the sync completes.
- **FAIL if:** It still does not appear after a manual sync.

## 2. Web → Supabase → Android

### Step 2.1 — Edit the test transaction on Web
- **Action:** On the **Web browser**, open the test transaction and change its **note** to `E2E-TEST-<initials>-<today>-EDITED` (or change the amount to `0.02`). Save.
- **Expect:** The edit is saved locally on Web and the row updates in the list.

### Step 2.2 — Confirm it propagated to Android
- **Action:** On the **Android app**, wait ~5–10 seconds (or tap the sync icon to force `forceSyncNow()`).
- **Expect:** The test transaction on Android now shows the **edited** note/amount. It must NOT show a duplicate — there must still be exactly **one** test transaction.
- **FAIL if:** The edit does not appear on Android, OR a second/duplicate test transaction appears (this would indicate a merge/dedup regression).
- **Where to check on FAIL:** [Appendix A](#appendix-a-where-to-find-the-transaction-id-and-state) — confirm there is exactly **one** row with the test note in `public.transactions`, and that its `id` is unchanged from Step 1.

## 3. Android Permanent Delete → Web

> **Important distinction:** "Delete" in the main list = **soft-delete to Trash** (`status='deleted'`). "Permanent delete" happens **inside the Trash bin** (the trash-can icon on the item, or "Empty Trash"). This step tests the **permanent** path.

### Step 3.1 — Soft-delete the test transaction on Android (move to Trash)
- **Action:** On the **Android app**, delete the test transaction from the main list (the normal delete action).
- **Expect:** It disappears from the main list and appears in the **Trash bin** on Android.
- **FAIL if:** It does not move to Trash, or an error appears.

### Step 3.2 — Permanently delete it from the Android Trash
- **Action:** On the **Android app**, open the **Trash bin**, find the test transaction, and tap its **permanent-delete (trash-can) icon**. Confirm the dialog.
- **Expect:** The item is removed from the Android Trash bin. A toast like "Οριστική διαγραφή / Permanently deleted" appears.

### Step 3.3 — Confirm it is gone on Web
- **Action:** On the **Web browser**, wait ~5–10 seconds (or force sync), then check **both** the main Transactions list **and** the Web Trash bin.
- **Expect:** The test transaction is **absent** from the Web main list **and** absent from the Web Trash bin. It must NOT reappear.
- **FAIL if:** The test transaction still shows on Web in the main list or the Trash bin after a manual sync.
- **Where to check on FAIL:** [Appendix A](#appendix-a-where-to-find-the-transaction-id-and-state) — query `public.transactions` for the note (expect **0 rows**), and `public.sync_tombstones` for `table_name='transactions'` and `row_id` = the test id (expect **1 row**).

## 4. Web Permanent Delete → Android

### Step 4.1 — Create a fresh test transaction on Web
- **Action:** On the **Web browser**, create a **new** expense transaction with the **same** test note string, amount `0.01`, today's date. Save.
- **Expect:** It appears on Web immediately.

### Step 4.2 — Confirm it reached Android
- **Action:** On the **Android app**, wait ~5–10 seconds (or force sync).
- **Expect:** The test transaction appears on Android (exactly one copy).

### Step 4.3 — Soft-delete it on Web (move to Trash)
- **Action:** On the **Web browser**, delete the test transaction from the main list.
- **Expect:** It moves to the Web Trash bin.

### Step 4.4 — Permanently delete it from the Web Trash
- **Action:** On the **Web browser**, open the Trash bin, find the test transaction, and tap its **permanent-delete icon** (or Empty Trash). Confirm.
- **Expect:** It is removed from the Web Trash bin.

### Step 4.5 — Confirm it is gone on Android
- **Action:** On the **Android app**, wait ~5–10 seconds (or force sync), then check the main list **and** the Android Trash bin.
- **Expect:** The test transaction is **absent** from both the Android main list and the Android Trash bin. It must NOT reappear.
- **FAIL if:** It still shows on Android in the main list or Trash after a manual sync.
- **Where to check on FAIL:** [Appendix A](#appendix-a-where-to-find-the-transaction-id-and-state) — same checks as Step 3.3 (0 rows in `transactions`, 1 tombstone in `sync_tombstones`).

## 5. Stale-Cache / Resurrection Scenario

This verifies that a permanently-deleted transaction can never be resurrected by a stale local cache or a re-fetch race.

### Step 5.1 — Create a test transaction on Android, then permanently delete it
- **Action:** On the **Android app**, create the test transaction again (same note, `0.01`). Wait for it to sync to the cloud (confirm it appears on Web). Then on Android: delete it to Trash, then **permanently delete** it from the Android Trash.
- **Expect:** It is gone from Android main list + Trash, and (after sync) gone from Web main list + Trash.

### Step 5.2 — Force repeated syncs on both devices
- **Action:** On **both** Android and Web, tap the sync icon (`forceSyncNow()`) **3 times in a row**, waiting ~5 seconds between taps. Then wait 30+ seconds (to exceed the 30s `_recentlyDeletedTxIds` grace window) and force sync **once more** on each device.
- **Expect:** The test transaction does **not** reappear on either device after any of these syncs.
- **FAIL if:** The test transaction reappears on Android or Web at any point after a sync (this is the resurrection bug).
- **Where to check on FAIL:** [Appendix A](#appendix-a-where-to-find-the-transaction-id-and-state) — check `public.transactions` (expect 0 rows) and `public.sync_tombstones` (expect the tombstone still present). Also check the local keys in [Appendix B](#appendix-b-local-storage-keys-to-inspect) — the id must be in `permanent_deleted_tx_ids` and absent from `offline_transactions`.

### Step 5.3 — Restore-then-permanent-delete edge (optional but recommended)
- **Action:** On Web, create the test transaction, soft-delete to Trash, then **Restore** it from the Trash. Confirm it returns to the main list on both devices. Then permanently delete it again from the Trash and confirm it is gone on both devices.
- **Expect:** Restore brings it back as `status='active'` on both devices; the subsequent permanent delete removes it everywhere.
- **FAIL if:** Restore does not bring it back on the other device, or the post-restore permanent delete leaves it on the other device.

## 6. Final Android / Web / Supabase Consistency Check

### Step 6.1 — Supabase ground truth
- **Action:** Run the following query (in the Supabase SQL editor or a DB client) for your account:
  ```sql
  SELECT id, date, type, amount, category, note, status, deleted_at, deleted_by, user_id
  FROM public.transactions
  WHERE note LIKE 'E2E-TEST-%'
  ORDER BY created_at DESC;
  ```
- **Expect:** **0 rows** (the test transaction is fully gone from the cloud).
- **FAIL if:** Any row returns. If a row returns with `status='deleted'`, the permanent delete did not hard-delete it. If `status='active'`, it was resurrected.

### Step 6.2 — Tombstone check
- **Action:** Run:
  ```sql
  SELECT table_name, row_id, deleted_at, user_id
  FROM public.sync_tombstones
  WHERE table_name = 'transactions'
  ORDER BY deleted_at DESC;
  ```
- **Expect:** A tombstone row exists for the test transaction's `row_id` (from the permanent delete). This is **expected and correct** — it is the durable guard that prevents resurrection.
- **FAIL if:** There is a tombstone but the transaction row still exists in `transactions` (inconsistent), or the tombstone is missing **and** the transaction is still present.

### Step 6.3 — Android local state
- **Action:** On Android, open the main list and the Trash bin.
- **Expect:** The test transaction is in **neither**.
- **FAIL if:** It appears in either.

### Step 6.4 — Web local state
- **Action:** On Web, open the main list and the Trash bin.
- **Expect:** The test transaction is in **neither**.
- **FAIL if:** It appears in either.

## Final Cleanup Checklist (verify the test transaction is fully removed)

Run through this only after all steps pass. It must confirm **zero** trace of the test transaction **without touching any real transaction**.

- [ ] `public.transactions` has **0 rows** with `note LIKE 'E2E-TEST-%'` (Step 6.1).
- [ ] Android main list: test transaction **absent**.
- [ ] Android Trash bin: test transaction **absent**.
- [ ] Web main list: test transaction **absent**.
- [ ] Web Trash bin: test transaction **absent**.
- [ ] Android local `offline_transactions` (see [Appendix B](#appendix-b-local-storage-keys-to-inspect)): test id **absent**.
- [ ] Android local `deleted_transactions_trash`: test id **absent**.
- [ ] Android local `permanent_deleted_tx_ids`: test id **present** (this is the correct, expected tombstone — do NOT remove it; it is what prevents resurrection).
- [ ] Web local `offline_transactions`: test id **absent**.
- [ ] Web local `deleted_transactions_trash`: test id **absent**.
- [ ] Web local `permanent_deleted_tx_ids`: test id **present** (expected tombstone).
- [ ] `public.sync_tombstones`: tombstone for the test `row_id` **present** (expected; do NOT delete it).
- [ ] **No real transaction** was created, edited, deleted, or restored during this test (verify by spot-checking that your real balances/notes are unchanged).

> **Note on the tombstones:** The `permanent_deleted_tx_ids` localStorage entries and the `sync_tombstones` row are **supposed** to remain. They are the durable guards that stop the deleted transaction from ever being resurrected. "Cleanup" means the transaction data is gone everywhere; the tombstones staying behind is correct behavior, not leftover test data.

## Appendix A — Where to Find the Transaction ID and State (on FAIL)

If a step fails, capture the transaction **id** and **state** from the authoritative source:

1. **Supabase `public.transactions`** (authoritative for existence + status):
   ```sql
   SELECT id, status, deleted_at, deleted_by, created_at, updated_at
   FROM public.transactions
   WHERE note = '<your-exact-test-note>';
   ```
   - `status = 'active'` → row is live.
   - `status = 'deleted'` → row is in Trash (soft-deleted).
   - **0 rows** → row was hard-deleted (permanent delete succeeded).

2. **Supabase `public.sync_tombstones`** (authoritative for permanent-delete propagation):
   ```sql
   SELECT row_id, deleted_at, user_id
   FROM public.sync_tombstones
   WHERE table_name = 'transactions' AND row_id = '<test-id>';
   ```
   - A row here means the permanent delete was recorded for propagation to other devices.

3. **Android / Web local state** (for cache-level diagnosis) — see [Appendix B](#appendix-b-local-storage-keys-to-inspect).

4. **How to get the id if you don't have it:** The id is a UUID. If the transaction still exists in the cloud, query `public.transactions` by note to get `id`. If it was already hard-deleted, query `public.sync_tombstones` by `deleted_at` around the test time, or check the local `permanent_deleted_tx_ids` list in the browser/WebView devtools.

## Appendix B — Local Storage Keys to Inspect

These are the localStorage keys the app uses for the transaction cache, trash, and permanent-delete guard. Inspect them in the Web browser devtools (Application → Local Storage) or the Android WebView devtools:

| Key | Meaning | Expected after permanent delete |
|---|---|---|
| `offline_transactions` | Local transaction cache | Test id **absent** |
| `deleted_transactions_trash` | Trash bin cache | Test id **absent** |
| `permanent_deleted_tx_ids` | Durable permanent-delete guard | Test id **present** (correct) |
| `money_manager_sync_queue` | Pending offline sync mutations | Test id **absent** (no stale save/delete queued) |

## Reference — Code Paths Verified by This Procedure

- **Save:** [`saveTransaction()`](app.js:5976) → optimistic local save → `enqueueSyncMutation('save')` → `upsert` to Supabase → `dequeueSyncMutation`.
- **Soft-delete (to Trash):** [`deleteTransaction()`](app.js:6065) → `status='deleted'`, `deleted_at`, `deleted_by` → `_markRecentlyDeleted()` (30s grace) → `writeSyncTombstones()`.
- **Restore:** [`restoreTransaction()`](app.js:34310) → flips `status='active'`, clears `deleted_at`/`deleted_by`.
- **Permanent delete (single):** [`deleteSingleTrashItem()`](app.js:36895) → hard `DELETE` row → `purgePermanentlyDeletedTxIds()` with cloud tombstone.
- **Permanent delete (empty):** [`emptyTrashBin()`](app.js:34355) → hard `DELETE` all `status='deleted'` rows → purge + tombstone.
- **Resurrection guard:** [`collectPermanentlyDeletedTxIds()`](app.js:4592) + [`mergeAndDeduplicateTransactions()`](js/transactionMerge.js:88) exclude permanently-deleted IDs from every merge/sync path.
- **Manual sync:** [`forceSyncNow()`](app.js:27050), triggered by the header sync icon ([`index.html`](index.html:444)) or the "Sync Now" row ([`index.html`](index.html:2208)).
