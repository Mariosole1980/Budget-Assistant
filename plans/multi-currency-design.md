# Υποστήριξη Πολλαπλών Νομισμάτων — Αρχιτεκτονικός Σχεδιασμός

**Σκοπός:** Σχεδιασμός μιας επεκτάσιμης, ακριβούς και offline-friendly αρχιτεκτονικής
για την υποστήριξη πολλαπλών νομισμάτων, που διατηρεί πάντα ακριβές το ιστορικό των
συναλλαγών και υπολογίζει σωστά όλα τα οικονομικά στοιχεία ανεξάρτητα από μελλοντικές
αλλαγές στις ισοτιμίες.

**Κατάσταση:** DESIGN REVIEW — πριν την υλοποίηση.

---

## 1. Το πρόβλημα (σύνοψη των προβληματισμών)

Ο χρήστης έχει βασικό νόμισμα **EUR**. Όλα τα υπάρχοντα δεδομένα (συναλλαγές,
στατιστικά, budgets, γραφήματα, αναφορές) υπολογίζονται σε ευρώ. Όταν ταξιδεύει στις
ΗΠΑ και πραγματοποιεί αγορά σε **USD**, προκύπτουν τα εξής κρίσιμα ερωτήματα:

1. Σε ποιο νόμισμα αποθηκεύεται η συναλλαγή;
2. Ποια ισοτιμία χρησιμοποιείται (στιγμή δημιουργίας vs τρέχουσα);
3. Τι εμφανίζεται στον χρήστη (πραγματικό ποσό, βασικό νόμισμα, ή και τα δύο);
4. Πώς υπολογίζονται στατιστικά, budgets, υπόλοιπα, αναφορές, διαγράμματα;
5. Τι γίνεται όταν αλλάζουν οι ισοτιμίες (αλλάζει η αξία παλιών συναλλαγών;);
6. Τι γίνεται αν αλλάξει το βασικό νόμισμα του λογαριασμού;
7. Offline λειτουργία (πώς γίνεται η μετατροπή χωρίς Internet);
8. Μελλοντική επεκτασιμότητα (οποιοδήποτε νόμισμα, πολλαπλά ταξίδια, πολλαπλοί
   λογαριασμοί, κοινά πορτοφόλια, επενδύσεις).

## 2. Τρέχουσα κατάσταση (baseline)

Η ανάλυση του υπάρχοντος κώδικα έδειξε τα εξής:

| Οντότητα | Τρέχον μοντέλο | Πρόβλημα |
|---|---|---|
| [`transactions`](supabase-schema.sql:58) | `amount NUMERIC(12,2)` — ένα μόνο ποσό, χωρίς νόμισμα | Δεν μπορεί να εκφράσει "πλήρωσα 50 USD" |
| [`accounts`](supabase-schema.sql:9) | `balance NUMERIC` — χωρίς νόμισμα | Όλοι οι λογαριασμοί θεωρούνται ίδιου νομίσματος |
| [`recurring_templates`](supabase-recurring-migration.sql:4) | `amount NUMERIC(12,2)` — χωρίς νόμισμα | Οι επαναλαμβανόμενες δεν έχουν νόμισμα |
| [`profiles`](family-budget-migration.sql:25) | `family_id`, `role` — χωρίς νόμισμα | Δεν υπάρχει "βασικό νόμισμα" ανά χρήστη |
| Budgets | `state.budgets` (localStorage: κατηγορία → όριο) | Όρια σε ένα μόνο νόμισμα |
| Display | `app_currency` (localStorage) → [`getCurrencySymbol()`](app.js:15464) | Αλλάζει ΜΟΝΟ το σύμβολο, όχι την αξία |

**Κρίσιμη παρατήρηση:** Όλα τα στατιστικά, τα υπόλοιπα και τα budgets υπολογίζονται
απευθείας από `parseFloat(t.amount)` (π.χ. [`calculateInitialBalances()`](app.js:3060),
στατιστικά στο [app.js:5837](app.js:5837), budgets στο [app.js:22088](app.js:22088)).
Δεν υπάρχει κανένα επίπεδο μετατροπής. Το `app_currency` επηρεάζει μόνο το σύμβολο
(€/$/£/¥) που εμφανίζεται — **όχι** την πραγματική αξία.

## 3. Η προτεινόμενη αρχιτεκτονική

### 3.1 Θεμελιώδης αρχή: "Αποθήκευσε το πραγματικό, υπολόγισε το εμφανιζόμενο"

Η βασική αρχή που λύνει όλα τα προβλήματα είναι:

> **Κάθε συναλλαγή αποθηκεύεται στο νόμισμα που πραγματικά έγινε, μαζί με την ισοτιμία
> της στιγμής εκείνης. Οποιαδήποτε μετατροπή σε άλλο νόμισμα γίνεται **κατά τον
> υπολογισμό/εμφάνιση** (on-the-fly), χρησιμοποιώντας πάντα την **αποθηκευμένη ισοτιμία
> της ημερομηνίας της συναλλαγής** — ποτέ την τρέχουσα.**

Αυτό διασφαλίζει:
- **Ακριβές ιστορικό:** Η πληροφορία "πλήρωσα 50 USD" διατηρείται αυτούσια.
- **Σταθερή αξία:** Μια συναλλαγή του περασμένου έτους ΔΕΝ αλλάζει αξία όταν αλλάζει
  η σημερινή ισοτιμία, γιατί χρησιμοποιείται πάντα η ισοτιμία της ημερομηνίας της.
- **Σωστά στατιστικά:** Όλα τα αθροίσματα γίνονται σε ένα κοινό νόμισμα (το βασικό),
  μετατρέποντας κάθε συναλλαγή με τη δική της ιστορική ισοτιμία.

### 3.2 Database Schema

#### 3.2.1 Πίνακας `currencies` (κατάλογος νομισμάτων)

```sql
CREATE TABLE public.currencies (
    code        TEXT PRIMARY KEY,          -- 'EUR', 'USD', 'GBP', 'JPY', ...
    name        TEXT NOT NULL,             -- 'Euro', 'US Dollar', ...
    symbol      TEXT NOT NULL,             -- '€', '$', '£', '¥', ...
    decimals    SMALLINT NOT NULL DEFAULT 2, -- π.χ. JPY = 0
    is_active   BOOLEAN NOT NULL DEFAULT true,
    created_at  TIMESTAMPTZ DEFAULT now()
);
```

**Γιατί:** Αποφεύγει hardcoded λίστες νομισμάτων στον κώδικα. Οποιοδήποτε νέο νόμισμα
προστίθεται ως εγγραφή, χωρίς αλλαγή στη λογική. Οι `decimals` είναι κρίσιμες για
σωστή στρογγυλοποίηση (π.χ. το JPY δεν έχει δεκαδικά).

#### 3.2.2 Πίνακας `exchange_rates` (ιστορικό ισοτιμιών)

```sql
CREATE TABLE public.exchange_rates (
    id          BIGSERIAL PRIMARY KEY,
    base_currency TEXT NOT NULL REFERENCES public.currencies(code), -- 'EUR'
    quote_currency TEXT NOT NULL REFERENCES public.currencies(code), -- 'USD'
    rate        NUMERIC(18,8) NOT NULL,    -- 1 EUR = X USD
    rate_date   DATE NOT NULL,             -- ημερομηνία ισχύος
    source      TEXT,                      -- 'api', 'manual', 'cached'
    created_at  TIMESTAMPTZ DEFAULT now(),
    UNIQUE (base_currency, quote_currency, rate_date)
);

-- Ευρετήριο για γρήγορη αναζήτηση ισοτιμίας συγκεκριμένης ημερομηνίας
CREATE INDEX idx_exchange_rates_lookup
    ON public.exchange_rates (base_currency, quote_currency, rate_date DESC);
```

**Γιατί:** Αποθηκεύει **ιστορικές** ισοτιμίες ανά ημερομηνία. Αυτό είναι το κλειδί για
να μην αλλάζει η αξία των παλιών συναλλαγών: η μετατροπή μιας συναλλαγής της
15/05/2026 χρησιμοποιεί πάντα την ισοτιμία της 15/05/2026, όχι τη σημερινή.

**Σημείωση για το `rate`:** Ορίζεται ως "1 μονάδα base = rate μονάδες quote". Η
αποθήκευση με 8 δεκαδικά αποφεύγει σφάλματα στρογγυλοποίησης σε ενδιάμεσους
υπολογισμούς.

#### 3.2.3 Τροποποίηση `transactions`

```sql
ALTER TABLE public.transactions
    ADD COLUMN currency TEXT NOT NULL DEFAULT 'EUR'
        REFERENCES public.currencies(code),
    ADD COLUMN amount_base NUMERIC(18,4),   -- ποσό στο βασικό νόμισμα (cache)
    ADD COLUMN base_currency TEXT,          -- βασικό νόμισμα κατά τη δημιουργία
    ADD COLUMN rate_to_base NUMERIC(18,8);  -- ισοτιμία currency → base εκείνη τη στιγμή
```

**Σημασιολογία των πεδίων:**
- `amount` (υπάρχον): το **πραγματικό** ποσό που πληρώθηκε, στο νόμισμα `currency`.
  Π.χ. `50.00` με `currency='USD'`.
- `currency`: το νόμισμα στο οποίο έγινε πραγματικά η συναλλαγή.
- `rate_to_base`: πόσες μονάδες `currency` αντιστοιχούν σε 1 μονάδα `base_currency`
  τη στιγμή της συναλλαγής. Π.χ. αν 1 EUR = 1.17 USD, τότε `rate_to_base = 1.17`.
- `amount_base`: το ποσό μετατρεπόμενο στο βασικό νόμισμα **τη στιγμή δημιουργίας**.
  Π.χ. `50 / 1.17 = 42.7350 EUR`.
- `base_currency`: το βασικό νόμισμα που ίσχυε όταν δημιουργήθηκε η συναλλαγή.

**Γιατί `amount_base` (cache) και όχι μόνο `rate_to_base`;**
- Ο υπολογισμός των στατιστικών γίνεται ταχύτατα αθροίζοντας `amount_base`, χωρίς να
  χρειάζεται join με τον πίνακα ισοτιμιών για κάθε συναλλαγή.
- Διατηρείται όμως και το `rate_to_base` για πλήρη διαφάνεια και δυνατότητα
  επανυπολογισμού (βλ. §6 αλλαγή βασικού νομίσματος).
- Το `base_currency` καταγράφει ποιο νόμισμα ήταν "βασικό" εκείνη τη στιγμή, ώστε αν
  αλλάξει αργότερα το βασικό νόμισμα να ξέρουμε σε τι αναφέρεται το `amount_base`.

> **Σημαντικό:** Το `amount_base` είναι **cache** για ταχύτητα, όχι η πηγή αλήθειας.
> Η πηγή αλήθειας είναι `(amount, currency, rate_to_base)`. Αν ποτέ χρειαστεί
> επανυπολογισμός, γίνεται από αυτά τα τρία πεδία.

#### 3.2.4 Τροποποίηση `accounts`

```sql
ALTER TABLE public.accounts
    ADD COLUMN currency TEXT NOT NULL DEFAULT 'EUR'
        REFERENCES public.currencies(code);
```

**Γιατί:** Κάθε λογαριασμός μπορεί να έχει το δικό του νόμισμα. Αυτό υποστηρίζει
"πολλαπλούς λογαριασμούς σε διαφορετικά νομίσματα" (π.χ. έναν τραπεζικό λογαριασμό σε
USD στις ΗΠΑ). Το `balance` του λογαριασμού είναι στο νόμισμα του λογαριασμού.

#### 3.2.5 Τροποποίηση `profiles` (βασικό νόμισμα χρήστη)

```sql
ALTER TABLE public.profiles
    ADD COLUMN base_currency TEXT NOT NULL DEFAULT 'EUR'
        REFERENCES public.currencies(code);
```

**Γιατί:** Το βασικό νόμισμα είναι ιδιότητα του **χρήστη** (ή του οικογενειακού
προφίλ), όχι του κώδικα. Αντικαθιστά το σημερινό `app_currency` του localStorage με
μια συγχρονισμένη, ανά-χρήστη τιμή. Σε οικογενειακό πλαίσιο, το βασικό νόμισμα μπορεί
να ορίζεται στο `family_groups` (βλ. §8).

#### 3.2.6 Τροποποίηση `recurring_templates`

```sql
ALTER TABLE public.recurring_templates
    ADD COLUMN currency TEXT NOT NULL DEFAULT 'EUR'
        REFERENCES public.currencies(code);
```

**Γιατί:** Μια επαναλαμβανόμενη συναλλαγή (π.χ. ενοίκιο) έχει σταθερό νόμισμα. Όταν
δημιουργείται κάθε μήνα η συναλλαγή, κληρονομεί το νόμισμα και χρησιμοποιεί την
ισοτιμία της ημερομηνίας δημιουργίας.

#### 3.2.7 Budgets

Τα budgets σήμερα είναι `state.budgets` (κατηγορία → όριο). Προτείνεται να
μεταφερθούν σε πίνακα με νόμισμα:

```sql
CREATE TABLE public.budgets (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID REFERENCES auth.users(id) ON DELETE CASCADE,
    family_id   UUID REFERENCES public.family_groups(id) ON DELETE SET NULL,
    category    TEXT NOT NULL,
    currency    TEXT NOT NULL DEFAULT 'EUR' REFERENCES public.currencies(code),
    limit_amount NUMERIC(12,2) NOT NULL,
    period      TEXT NOT NULL DEFAULT 'monthly', -- 'monthly', 'yearly'
    created_at  TIMESTAMPTZ DEFAULT now(),
    UNIQUE (user_id, category, period)
);
```

**Γιατί:** Το όριο ενός budget ορίζεται σε ένα συγκεκριμένο νόμισμα (συνήθως το
βασικό). Η σύγκριση με τα πραγματικά έξοδα γίνεται αφού μετατραπούν τα έξοδα στο
νόμισμα του budget.

### 3.3 Μοντέλο δεδομένων (client-side)

Στο `app.js`, κάθε συναλλαγή στο `state.transactions` θα έχει:

```js
{
  id: '...',
  date: '2026-05-15',
  type: 'expense',
  amount: 50.00,          // πραγματικό ποσό (USD)
  currency: 'USD',        // νόμισμα συναλλαγής
  rate_to_base: 1.17,     // 1 EUR = 1.17 USD εκείνη τη στιγμή
  amount_base: 42.7350,   // 50 / 1.17 = 42.7350 EUR (cache)
  base_currency: 'EUR',   // βασικό νόμισμα κατά τη δημιουργία
  category: '...',
  account_from: '...',
  // ...
}
```

**Συμβατότητα προς τα πίσω:** Τα υπάρχοντα πεδία `amount`, `type`, `category`,
`account_from`, κ.λπ. παραμένουν. Τα νέα πεδία έχουν defaults (`currency='EUR'`,
`rate_to_base=1`, `amount_base=amount`, `base_currency='EUR'`), οπότε όλες οι
υπάρχουσες συναλλαγές συνεχίζουν να λειτουργούν χωρίς αλλαγή.

### 3.4 Ροή μετατροπής (Conversion Flow)

#### 3.4.1 Δημιουργία συναλλαγής σε ξένο νόμισμα

```
Χρήστης εισάγει: 50 USD, ημερομηνία 15/05/2026
        │
        ▼
1. Βρες την ισοτιμία EUR→USD για την 15/05/2026
   (από exchange_rates· αν λείπει, από το πιο πρόσφατο cached rate)
        │
        ▼
2. rate_to_base = 1.17  (1 EUR = 1.17 USD)
        │
        ▼
3. amount_base = 50 / 1.17 = 42.7350 EUR
        │
        ▼
4. Αποθήκευσε: { amount: 50, currency: 'USD', rate_to_base: 1.17,
                 amount_base: 42.7350, base_currency: 'EUR' }
```

#### 3.4.2 Εμφάνιση στη λίστα συναλλαγών

Ο χρήστης βλέπει **και τα δύο** (απάντηση στον προβληματισμό 3):

- **Κύριο:** το πραγματικό ποσό που πλήρωσε — `50,00 $` (με το σύμβολο του νομίσματος
  της συναλλαγής).
- **Δευτερεύον (μικρότερο, γκρι):** το ισοδύναμο στο βασικό νόμισμα — `≈ 42,74 €`.

Αυτό δίνει στον χρήστη και την πραγματική πληροφορία (τι πλήρωσε) και το πλαίσιο για
τα στατιστικά (τι σημαίνει για τον προϋπολογισμό του).

#### 3.4.3 Υπολογισμός στατιστικών, budgets, υπόλοιπων, αναφορών, διαγραμμάτων

Όλα τα αθροίσματα γίνονται **πάντα στο βασικό νόμισμα**, αθροίζοντας το `amount_base`
κάθε συναλλαγής (απάντηση στον προβληματισμό 4):

```js
// Παράδειγμα: συνολικά έξοδα του μήνα στο βασικό νόμισμα
const monthlyExpense = transactions
  .filter(t => t.type === 'expense' && isInMonth(t.date))
  .reduce((sum, t) => sum + (t.amount_base ?? 0), 0);
```

**Γιατί χρησιμοποιούμε `amount_base` και όχι `amount`:** Γιατί το `amount` είναι στο
νόμισμα της συναλλαγής (π.χ. USD) και δεν μπορεί να αθροιστεί με ευρώ. Το `amount_base`
είναι ήδη μετατρεμμένο στο βασικό νόμισμα με την ιστορική ισοτιμία.

**Γιατί όχι τρέχουσα ισοτιμία:** Αν χρησιμοποιούσαμε τη σημερινή ισοτιμία για όλες
τις συναλλαγές, τότε κάθε μέρα που αλλάζει η ισοτιμία θα άλλαζαν όλα τα ιστορικά
αθροίσματα — ακριβώς αυτό που θέλουμε να αποφύγουμε (προβληματισμός 5).

### 3.5 Αποθήκευση ισοτιμιών (Rate Storage)

#### 3.5.1 Πηγές ισοτιμιών — από πού αντλείται η ισοτιμία της ημέρας

Η ισοτιμία της ημέρας αντλείται από **τρεις πηγές**, σε ιεραρχία προτεραιότητας:

| Προτεραιότητα | Πηγή | Πότε χρησιμοποιείται | `source` |
|---|---|---|---|
| 1 | **Online API** | Όταν υπάρχει σύνδεση και το API απαντά | `'api'` |
| 2 | **Χειροκίνητη εισαγωγή** | Όταν ο χρήστης την ορίζει ρητά (π.χ. από την τράπεζά του) | `'manual'` |
| 3 | **Cached / τελευταία γνωστή** | Offline ή όταν λείπει η ισοτιμία της ημερομηνίας | `'cached'` |

##### (α) Online API — η κύρια πηγή

Προτείνονται δωρεάν APIs που δεν απαιτούν κλειδί (ή έχουν γενναιόδωρο free tier) και
ταιριάζουν με το μοντέλο "ιστορική ισοτιμία ανά ημερομηνία":

- **Frankfurter (ECB)** — `https://api.frankfurter.app/{date}?from=EUR&to=USD`
  - Δωρεάν, χωρίς κλειδί, βασισμένο στα επίσημα δεδομένα της Ευρωπαϊκής Κεντρικής
    Τράπεζας. Υποστηρίζει **ιστορικές ημερομηνίες** (π.χ. `2026-05-15`), που είναι
    ακριβώς αυτό που χρειαζόμαστε για backfill παλιών συναλλαγών.
  - **Περιορισμός:** οι ισοτιμίες δημοσιεύονται μόνο για **εργάσιμες ημέρες** (όχι
    Σαββατοκύριακα/αργίες). Για Σαββατοκύριακο χρησιμοποιούμε την τελευταία εργάσιμη.
- **open.er-api.com** — `https://open.er-api.com/v6/latest/EUR`
  - Δωρεάν, χωρίς κλειδί, δίνει την **τρέχουσα** ισοτιμία (όχι ιστορική). Καλό για τη
    σημερινή ημερομηνία.
- **exchangerate-api.com** — δωρεάν tier με κλειδί, υποστηρίζει ιστορικές ημερομηνίες.

**Σύσταση:** Χρησιμοποιούμε το **Frankfurter** ως κύρια πηγή γιατί καλύπτει και
ιστορικές ημερομηνίες (κρίσιμο για backfill) και είναι δωρεάν χωρίς κλειδί. Αν
χρειαστεί redundancy, προσθέτουμε το open.er-api.com ως fallback για τη σημερινή
ημερομηνία.

##### (β) Χειροκίνητη εισαγωγή

Ο χρήστης μπορεί να εισάγει χειροκίνητα την ισοτιμία (π.χ. από την τράπεζά του ή από
ένα ανταλλακτήριο). Αυτό είναι απαραίτητο για:
- **Offline** λειτουργία (προβληματισμός 7).
- Όταν ο χρήστης θέλει να χρησιμοποιήσει **τη δική του** ισοτιμία (π.χ. την πραγματική
  χρέωση της κάρτας του, που συχνά διαφέρει από την επίσημη).

Η χειροκίνητη ισοτιμία αποθηκεύεται με `source='manual'` και **δεν αντικαθίσταται**
αυτόματα από το API όταν επανέλθει η σύνδεση.

##### (γ) Cached / τελευταία γνωστή

Κάθε ισοτιμία που λαμβάνεται (από API ή χειροκίνητα) αποθηκεύεται και **τοπικά**
(localStorage/IndexedDB) για offline χρήση. Όταν δεν υπάρχει σύνδεση ή λείπει η
ισοτιμία της συγκεκριμένης ημερομηνίας, χρησιμοποιείται η **πλησιέστερη προηγούμενη**
γνωστή ισοτιμία, με `source='cached'`.

#### 3.5.2 Στρατηγική ενημέρωσης (πότε και πώς φέρνουμε την ισοτιμία)

Η εφαρμογή ακολουθεί αυτή τη ροή για να εξασφαλίσει ότι έχει πάντα διαθέσιμη την
ισοτιμία της ημέρας:

```
Εκκίνηση εφαρμογής (ή επαναφορά σύνδεσης)
        │
        ▼
1. Έλεγξε τοπικό cache: υπάρχει ισοτιμία για ΣΗΜΕΡΑ;
        │
        ├── ΝΑΙ → χρησιμοποίησέ την (source='cached') — δεν χρειάζεται δίκτυο
        │
        └── ΟΧΙ → υπάρχει σύνδεση;
                  ├── ΝΑΙ → κάλεσε το API (Frankfurter) για σήμερα
                  │         → αποθήκευσε στον exchange_rates (rate_date=σήμερα)
                  │         → αποθήκευσε και στο τοπικό cache
                  └── ΟΧΙ → χρησιμοποίησε την τελευταία γνωστή (source='cached')
```

**Κανόνες:**

- Κατά την εκκίνηση (ή όταν υπάρχει σύνδεση), η εφαρμογή φέρνει τις ισοτιμίες για
  **σήμερα** και τις αποθηκεύει στον πίνακα `exchange_rates` με `rate_date = σήμερα`.
- Οι ισοτιμίες είναι **append-only** (ιστορικό). Ποτέ δεν διαγράφονται/αντικαθίστανται
  παλιές εγγραφές — προστίθενται νέες ανά ημερομηνία.
- Όταν μια συναλλαγή δημιουργείται για μια ημερομηνία χωρίς αποθηκευμένη ισοτιμία,
  χρησιμοποιείται η **πλησιέστερη προηγούμενη** γνωστή ισοτιμία (fallback), και
  σημειώνεται ως `source='cached'`.
- **Backfill ιστορικού:** Όταν ενεργοποιηθεί η υποστήριξη πολλαπλών νομισμάτων, το
  Frankfurter μπορεί να δώσει ισοτιμίες για **παλιές ημερομηνίες** (π.χ. όλες οι
  συναλλαγές του τελευταίου έτους), ώστε να υπολογιστούν σωστά τα `amount_base` των
  υπαρχουσών συναλλαγών σε ξένο νόμισμα.
- **Συχνότητα:** Οι ισοτιμίες αλλάζουν καθημερινά, οπότε αρκεί μία λήψη ανά ημέρα.
  Δεν χρειάζεται real-time polling — μόνο κατά την εκκίνηση και όταν δημιουργείται
  συναλλαγή σε ξένο νόμισμα.

#### 3.5.3 Offline λειτουργία (προβληματισμός 7)

- Αν δεν υπάρχει σύνδεση, χρησιμοποιείται η **τελευταία γνωστή ισοτιμία** από το
  τοπικό cache.
- Ο χρήστης μπορεί να **εισάγει χειροκίνητα** την ισοτιμία (π.χ. από την τράπεζά του).
  Αυτή αποθηκεύεται ως `source='manual'` και χρησιμοποιείται για τη συναλλαγή.
- Όταν επανέλθει η σύνδεση, οι χειροκίνητες ισοτιμίες **δεν αντικαθίστανται** αυτόματα
  — παραμένουν ως έχουν, γιατί η συναλλαγή που δημιουργήθηκε με αυτές πρέπει να
  παραμείνει σταθερή.

### 3.6 Ενιαίο επίπεδο μετατροπής (Conversion Service)

Προτείνεται ένα κεντρικό module (π.χ. `js/CurrencyService.js`) που συγκεντρώνει όλη τη
λογική μετατροπής, ώστε να μην διασπείρεται στον κώδικα:

```js
const CurrencyService = {
  // Μετατρέπει ποσό από ένα νόμισμα σε άλλο με ιστορική ισοτιμία
  convert(amount, fromCurrency, toCurrency, date) { ... },

  // Υπολογίζει το amount_base μιας νέας συναλλαγής
  computeAmountBase(amount, currency, baseCurrency, date) { ... },

  // Επιστρέφει το ποσό μιας συναλλαγής στο βασικό νόμισμα (χρησιμοποιεί amount_base)
  toBase(tx) { return tx.amount_base ?? tx.amount; },

  // Επιστρέφει το ποσό μιας συναλλαγής σε οποιοδήποτε νόμισμα (για εμφάνιση)
  displayAmount(tx, targetCurrency) { ... },

  // Φέρνει την ισοτιμία της ημέρας από το API (Frankfurter) και την αποθηκεύει
  // στον exchange_rates + στο τοπικό cache. Επιστρέφει true αν επιτυχία.
  async fetchTodayRates(baseCurrency) { ... },

  // Επιστρέφει την ισοτιμία base→quote για μια ημερομηνία, με ιεραρχία:
  //  1) exchange_rates (ακριβής ημερομηνία) → 2) χειροκίνητη → 3) πλησιέστερη προηγούμενη
  getRate(base, quote, date) { ... },

  // Ο χρήστης ορίζει χειροκίνητα ισοτιμία (source='manual', δεν αντικαθίσταται)
  setManualRate(base, quote, date, rate) { ... },
};
```

**Γιατί:** Όλα τα σημεία του κώδικα που σήμερα κάνουν `parseFloat(t.amount)` θα
καλούν `CurrencyService.toBase(t)` ή `CurrencyService.displayAmount(t, ...)`. Αυτό
κεντροποιεί τη λογική και επιτρέπει μελλοντικές αλλαγές (π.χ. νέο API ισοτιμιών) σε
ένα μόνο σημείο.

### 3.7 UX Επιλογής Νομίσματος

Η εφαρμογή υποστηρίζει τεχνικά **όλα** τα παγκόσμια νομίσματα, αλλά ο χρήστης δεν
πρέπει ποτέ να ψάχνει μέσα σε εκατοντάδες νομίσματα. Η επιλογή νομίσματος γίνεται με
μια **έξυπνη, φιλτραρισμένη λίστα** που προτείνει το σωστό νόμισμα αυτόματα.

#### 3.7.1 Διαχωρισμός: Πλήρης κατάλογος (DB) vs Έξυπνη λίστα (UI)

- **Πλήρης κατάλογος (βάση):** Ο πίνακας `currencies` περιέχει όλα τα νομίσματα του
  κόσμου (κωδικός, όνομα, σύμβολο, σημαία, χώρες, `decimals`). Αυτός είναι η πηγή
  αλήθειας — πλήρης και σταθερός.
- **Έξυπνη λίστα (UI):** Το UI εμφανίζει **μόνο** ένα φιλτραρισμένο υποσύνολο,
  βασισμένο σε προτεραιότητες. Ο χρήστης βλέπει λίγες, σχετικές επιλογές — όχι
  εκατοντάδες.

```
Πλήρης κατάλογος (currencies table)          Έξυπνη λίστα (UI)
┌──────────────────────────────┐             ┌──────────────────────────────┐
│ USD, EUR, GBP, JPY, CAD,     │   → φίλτρο →│ 🇺🇸 USD - Δολάριο ΗΠΑ        │
│ AUD, CHF, CNY, INR, ...      │             │ 🇪🇺 EUR - Ευρώ               │
│ (180+ νομίσματα)             │             │ 🇯🇵 JPY - Γιεν Ιαπωνίας      │
└──────────────────────────────┘             │ 🔍 Αναζήτηση...              │
                                             └──────────────────────────────┘
```

#### 3.7.2 Δομή της έξυπνης λίστας (με σειρά προτεραιότητας)

Η λίστα εμφανίζει τα νομίσματα με την εξής ιεραρχία:

1. **Αυτόματη πρόταση από account:** Αν ο χρήστης επέλεξε account, το νόμισμά του
   εμφανίζεται πρώτο (προεπιλογή). Ο χρήστης συνήθως δεν χρειάζεται να επιλέξει.
2. **Αυτόματη πρόταση από χώρα:** Αν η εφαρμογή γνωρίζει τη χώρα (GPS, γλώσσα,
   χειροκίνητη ρύθμιση), προτείνει το τοπικό νόμισμα (π.χ. Ιαπωνία → JPY). Ιδανικό
   για ταξίδια.
3. **Πρόσφατα χρησιμοποιημένα:** Τα νομίσματα που χρησιμοποίησε πρόσφατα ο χρήστης
   (αποθηκεύονται ανά χρήστη).
4. **Προτεινόμενα δημοφιλή:** Τα πιο συνηθισμένα παγκοσμίως (EUR, USD, GBP, JPY, CAD,
   AUD, CHF, CNY, INR).
5. **Αναζήτηση:** Ο χρήστης μπορεί να ψάξει με κωδικό, όνομα ή χώρα.

#### 3.7.3 Αναζήτηση (3 τρόποι)

Η αναζήτηση υποστηρίζει τρεις τρόπους ταυτόχρονα:

| Τρόπος | Παράδειγμα | Τι ταιριάζει |
|---|---|---|
| **Κωδικός** | `USD` | Ο κωδικός ISO 4217 |
| **Όνομα** | `δολάριο` | Το όνομα του νομίσματος (σε πολλές γλώσσες) |
| **Χώρα** | `Αμερική` | Η χώρα/περιοχή που χρησιμοποιεί το νόμισμα |

```js
// Παράδειγμα φίλτρου αναζήτησης
function filterCurrencies(query, allCurrencies) {
  const q = query.trim().toLowerCase();
  return allCurrencies.filter(c =>
    c.code.toLowerCase().includes(q) ||          // κωδικός: "usd"
    c.name.toLowerCase().includes(q) ||          // όνομα: "δολάριο"
    c.countries.some(ct => ct.toLowerCase().includes(q)) // χώρα: "αμερική"
  );
}
```

#### 3.7.4 Σωστή εμφάνιση: Σημαία + Κωδικός + Όνομα

Κάθε νόμισμα εμφανίζεται με **σημαία + κωδικό + όνομα**, όχι μόνο με το σύμβολο:

```
🇺🇸 USD - Δολάριο ΗΠΑ
🇪🇺 EUR - Ευρώ
🇯🇵 JPY - Γιεν Ιαπωνίας
```

- **Σημαία:** Από το emoji της χώρας (ή της κύριας χώρας του νομίσματος).
- **Κωδικός:** Ο κωδικός ISO 4217 (USD, EUR, JPY).
- **Όνομα:** Το πλήρες όνομα του νομίσματος στη γλώσσα του χρήστη.

Το σύμβολο (`$`, `€`, `¥`) χρησιμοποιείται **μόνο** στην εμφάνιση ποσών, όχι στην
επιλογή νομίσματος (γιατί το `$` είναι διφορούμενο — USD, CAD, AUD).

#### 3.7.5 Σχήμα του πίνακα `currencies` (με σημαία & χώρες)

```sql
CREATE TABLE public.currencies (
    code        TEXT PRIMARY KEY,          -- ISO 4217 (USD)
    name        TEXT NOT NULL,             -- "US Dollar"
    name_local  TEXT,                      -- "Δολάριο ΗΠΑ" (γλώσσα χρήστη)
    symbol      TEXT NOT NULL,             -- "$"
    flag        TEXT,                      -- emoji σημαίας "🇺🇸"
    countries   TEXT[],                    -- ["United States", "Ecuador", ...]
    decimals    SMALLINT NOT NULL DEFAULT 2,
    is_popular  BOOLEAN NOT NULL DEFAULT false,  -- για "προτεινόμενα"
    is_active   BOOLEAN NOT NULL DEFAULT true,
    created_at  TIMESTAMPTZ DEFAULT now()
);
```

#### 3.7.6 Αποθήκευση "πρόσφατων" ανά χρήστη

Τα πρόσφατα νομίσματα αποθηκεύονται ανά χρήστη (για προσωπική εμπειρία):

```sql
CREATE TABLE public.user_recent_currencies (
    user_id    UUID REFERENCES auth.users(id) ON DELETE CASCADE,
    currency   TEXT REFERENCES public.currencies(code),
    last_used  TIMESTAMPTZ DEFAULT now(),
    PRIMARY KEY (user_id, currency)
);
```

Το UI εμφανίζει τα πρόσφατα με βάση το `last_used` (πιο πρόσφατα πρώτα), περιορισμένα
σε ~5 για να μην γεμίζει η λίστα.

#### 3.7.7 Κανόνες UX

1. **Ποτέ τεχνικοί όροι** — ο χρήστης βλέπει μόνο "Νόμισμα", "Ποσό", "Ισοτιμία".
2. **Αυτόματη επιλογή:** Αν το νόμισμα προκύπτει από account/χώρα, επιλέγεται αυτόματα
   — ο χρήστης δεν το σκέφτεται.
3. **Αυτόματη μετατροπή:** Ο χρήστης βλέπει "5 USD = 4.27 EUR" χωρίς να κάνει τίποτα.
4. **Χειροκίνητη ισοτιμία κρυμμένη:** Πίσω από "Προχωρημένες επιλογές".
5. **Σαφής ένδειξη εκτίμησης:** Αν η ισοτιμία είναι cached (offline), "⚠️ Εκτίμηση".
6. **Λίστα μικρή:** Η έξυπνη λίστα δείχνει λίγες επιλογές (πρόσφατα + προτεινόμενα),
   με αναζήτηση για οτιδήποτε άλλο.

**Στόχος:** Η εφαρμογή υποστηρίζει παγκόσμια νομίσματα **τεχνικά**, αλλά η εμπειρία
χρήσης παραμένει **απλή** — ο χρήστης βλέπει το σωστό νόμισμα χωρίς να ψάχνει.

## 4. Απαντήσεις στους προβληματισμούς

### 4.1 Σε ποιο νόμισμα αποθηκεύεται η συναλλαγή;

**Στο πραγματικό νόμισμα** (`amount` + `currency`), **και** αποθηκεύεται το ισοδύναμο
στο βασικό (`amount_base`) με την ιστορική ισοτιμία. Έτσι δεν χάνεται ούτε η
πραγματική πληροφορία (50 USD) ούτε η δυνατότητα σωστού υπολογισμού σε ευρώ.

### 4.2 Ποια ισοτιμία χρησιμοποιείται;

**Η ισοτιμία της ημερομηνίας της συναλλαγής** (ιστορική), αποθηκευμένη ως
`rate_to_base` στο ίδιο το record. Ποτέ η τρέχουσα. Αυτό εγγυάται ότι οι παλιές
συναλλαγές δεν αλλάζουν αξία.

### 4.3 Τι εμφανίζεται στον χρήστη;

**Και τα δύο:** το πραγματικό ποσό (50,00 $) ως κύριο, και το ισοδύναμο στο βασικό
νόμισμα (≈ 42,74 €) ως δευτερεύον. Ο χρήστης έχει πλήρη εικόνα.

### 4.4 Πώς υπολογίζονται τα στατιστικά;

Όλα τα αθροίσματα (έξοδα, έσοδα, υπόλοιπο, budget, αναφορές, διαγράμματα)
υπολογίζονται **στο βασικό νόμισμα**, αθροίζοντας το `amount_base` κάθε συναλλαγής.
Αυτό είναι πάντα σωστό γιατί κάθε `amount_base` είναι ήδη στο βασικό νόμισμα με την
ιστορική ισοτιμία.

### 4.5 Τι συμβαίνει αν αλλάξουν οι ισοτιμίες;

**Τίποτα.** Μια συναλλαγή του περασμένου έτους έχει σταθερό `amount_base` που
υπολογίστηκε με την ισοτιμία της ημερομηνίας της. Η σημερινή αλλαγή ισοτιμίας
επηρεάζει μόνο τις **νέες** συναλλαγές. Το ιστορικό παραμένει ακριβές.

### 4.6 Τι γίνεται αν αλλάξει το βασικό νόμισμα;

Δεν αλλάζουμε αυτόματα τις παλιές συναλλαγές. Προσφέρουμε **προαιρετικό
επανυπολογισμό**:

- **Προεπιλογή:** Οι παλιές συναλλαγές μένουν ως έχουν. Το `amount_base` τους
  αναφέρεται στο παλιό `base_currency` (καταγεγραμμένο). Τα ιστορικά στατιστικά
  εμφανίζονται στο νέο βασικό νόμισμα **μετατρέποντας on-the-fly** από το
  `amount_base` (παλιό βασικό) στο νέο βασικό, χρησιμοποιώντας την ισοτιμία της
  ημερομηνίας κάθε συναλλαγής.
- **Προαιρετικός επανυπολογισμός:** Ο χρήστης μπορεί να επιλέξει "Επανυπολογισμός
  όλων στο νέο βασικό νόμισμα". Τότε το `amount_base` κάθε συναλλαγής ξαναυπολογίζεται
  από `(amount, currency, rate_to_base)` και ενημερώνεται το `base_currency='USD'`.
  Αυτό είναι ασφαλές γιατί η πηγή αλήθειας (`amount`, `currency`, `rate_to_base`)
  παραμένει άθικτη.

### 4.7 Offline λειτουργία;

Χρησιμοποιείται η **τελευταία γνωστή ισοτιμία** από το τοπικό cache, ή **χειροκίνητη
εισαγωγή** από τον χρήστη. Οι χειροκίνητες ισοτιμίες δεν αντικαθίστανται αυτόματα όταν
επανέλθει η σύνδεση.

### 4.8 Μελλοντική επεκτασιμότητα;

- **Οποιοδήποτε νόμισμα:** προσθήκη εγγραφής στον πίνακα `currencies`.
- **Πολλαπλά ταξίδια:** κάθε συναλλαγή έχει το δικό της νόμισμα/ισοτιμία — δεν υπάρχει
  έννοια "ταξιδιού" που να περιορίζει.
- **Πολλαπλοί λογαριασμοί σε διαφορετικά νομίσματα:** κάθε `account` έχει δικό του
  `currency`.
- **Κοινά πορτοφόλια / επενδύσεις / επιχειρηματικά έξοδα:** το μοντέλο
  `(amount, currency, rate_to_base, amount_base)` είναι γενικό και καλύπτει κάθε
  οικονομική οντότητα. Οι επενδύσεις μπορούν να προσθέσουν `cost_basis` ανά νόμισμα
  χωρίς αλλαγή στη δομή.

## 5. Σύγκριση εναλλακτικών προσεγγίσεων

| Προσέγγιση | Πλεονεκτήματα | Μειονεκτήματα | Απόφαση |
|---|---|---|---|
| **A. Μόνο βασικό νόμισμα** (status quo) | Απλό | Χάνεται η πραγματική πληροφορία (50 USD) | ❌ |
| **B. Μόνο πραγματικό νόμισμα** | Ακριβές ιστορικό | Δεν μπορούν να αθροιστούν στατιστικά | ❌ |
| **C. Πραγματικό + ιστορική ισοτιμία + cache βασικού** (προτεινόμενο) | Ακριβές ιστορικό, σωστά στατιστικά, σταθερή αξία, offline, επεκτάσιμο | Λίγο πιο σύνθετο schema | ✅ |
| **D. Πραγματικό + τρέχουσα ισοτιμία** | Απλό | Οι παλιές συναλλαγές αλλάζουν αξία καθημερινά | ❌ |

Η προσέγγιση **C** είναι η μόνη που ικανοποιεί ταυτόχρονα όλα τα κριτήρια του στόχου:
ακριβές ιστορικό, σωστά οικονομικά στοιχεία, ανεξαρτησία από μελλοντικές αλλαγές
ισοτιμιών, offline λειτουργία και εύκολη επέκταση χωρίς αλλαγή στη βάση ή στη λογική.

## 6. Στρατηγική μετάβασης (Migration)

Για να μην σπάσει η υπάρχουσα εφαρμογή:

1. **Προσθήκη πεδίων με defaults** (`currency='EUR'`, `rate_to_base=1`,
   `amount_base=amount`, `base_currency='EUR'`) — όλες οι υπάρχουσες συναλλαγές
   παραμένουν έγκυρες.
2. **Backfill:** Ένα migration script ενημερώνει τα υπάρχοντα records ώστε
   `currency='EUR'`, `rate_to_base=1`, `amount_base=amount`, `base_currency='EUR'`.
3. **Σταδιακή αντικατάσταση** των `parseFloat(t.amount)` με `CurrencyService.toBase(t)`
   στα σημεία υπολογισμού στατιστικών/υπολοίπων/budgets.
4. **UI:** Προσθήκη επιλογής νομίσματος στη φόρμα συναλλαγής (με προεπιλογή το νόμισμα
   του επιλεγμένου λογαριασμού), και εμφάνιση του διπλού ποσού (πραγματικό + βασικό)
   στη λίστα.
5. **Ισοτιμίες:** Δημιουργία πινάκων `currencies` και `exchange_rates`, και αρχική
   φόρτωση ισοτιμιών για το ζεύγος EUR→USD (και όσα άλλα χρειαστούν).
6. **Δοκιμές:** Επαλήθευση ότι τα υπάρχοντα στατιστικά/υπόλοιπα παραμένουν ίδια μετά
   το backfill (αφού όλες οι παλιές συναλλαγές έχουν `currency='EUR'`).

## 7. Συμπέρασμα

Η προτεινόμενη αρχιτεκτονική βασίζεται σε μία απλή αλλά ισχυρή αρχή:

> **Αποθήκευσε το πραγματικό ποσό στο πραγματικό νόμισμα, μαζί με την ιστορική
> ισοτιμία της ημερομηνίας της συναλλαγής. Υπολόγισε όλα τα οικονομικά στοιχεία στο
> βασικό νόμισμα χρησιμοποιώντας πάντα αυτή την ιστορική ισοτιμία.**

Αυτό επιτυγχάνει όλους τους στόχους:

- ✅ **Ακριβές ιστορικό** — το "πλήρωσα 50 USD" διατηρείται αυτούσιο.
- ✅ **Σωστά οικονομικά στοιχεία** — όλα τα αθροίσματα γίνονται στο βασικό νόμισμα.
- ✅ **Ανεξαρτησία από μελλοντικές αλλαγές ισοτιμιών** — οι παλιές συναλλαγές έχουν
  σταθερή αξία.
- ✅ **Offline λειτουργία** — τελευταία γνωστή ή χειροκίνητη ισοτιμία.
- ✅ **Εύκολη επέκταση** — νέα νομίσματα, λογαριασμοί, ταξίδια και οντότητες
  προστίθενται χωρίς αλλαγή στη βάση ή στη λογική.

Το μοντέλο `(amount, currency, rate_to_base, amount_base, base_currency)` είναι το
ελάχιστο πλήρες σύνολο πεδίων που ικανοποιεί όλες τις απαιτήσεις, διατηρώντας πλήρη
συμβατότητα με τα υπάρχοντα δεδομένα μέσω defaults. Η υλοποίηση μπορεί να ξεκινήσει
με τη δημιουργία του `CurrencyService` και τη σταδιακή αντικατάσταση των σημείων
υπολογισμού, χωρίς να διαταραχθεί η υπάρχουσα λειτουργία.
